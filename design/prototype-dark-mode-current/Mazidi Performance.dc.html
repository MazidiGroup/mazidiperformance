9dEvent taxonomy, badges & deep links — spec
Notification system rules
Event types → destination
Discomfort report → report detail (5d) · Check-in submitted → review (2c) · Progression met → approval (9c) · Missed workout / adherence drop → client profile · Invitation sent/opened/accepted/expired → invitation (8b) · Message → conversation · Renewal & payment → packages · Client sync failed → client profile banner
Priority dots
Amber = needs action and red = system problem — both always carry a text label (“Needs action”, “Sync issue”, “Awaiting you”). Blue = informational unread, shown by dot + bold title; read rows have neither. Colour is never the only signal.
Badges
Read state (unread/read) and task state (needs action/acknowledged/resolved) are independent. The badge counts unresolved needs-action items regardless of read state — opening a report or “Mark all read” never clears it; only Acknowledge or Resolve does. Snoozed items don’t count until they resurface.
Grouping & quiet hours
Same-type events within an hour collapse (“3 check-ins submitted”). Non-urgent pushes respect coach quiet hours (settable); discomfort alerts marked “notify now” bypass quiet hours when notification permission and connectivity allow; otherwise they surface immediately on next app open.
History
Resolved items live in a searchable 12-month history, opened from the search icon in the inbox header; state changes are timestamped (who/when) for accountability.

8iInvitation edge states — spec
Invitation & onboarding edge states
Expired / revoked / already used
Landing explains plainly (“This invitation has expired”) with one action: “Ask Jordan to resend”. Used links route a signed-in Sarah straight into the app.
Duplicate client
Email already coached by Jordan → merge into the existing record, never a second profile. Coached by another coach → Sarah chooses to add a concurrent coach or switch. Offline mid-onboarding
Setup answers save on-device and sync on reconnect; only account creation and code verification need a connection, and both fail with plain retry states.
Coaching relationship ends
Coach access ends immediately; Sarah keeps her account, history and photos, and can accept a new coach’s invitation later. Pending invitations from an ended relationship are auto-revoked.

Rest timer is an end-timestamp, not a running counter — it stays accurate and fires a local notification/haptic (respecting silent mode; sound & haptic preference in Settings). If notifications are denied, an in-app banner + sound covers rest-end alerts. Pausing or ending a workout cancels scheduled alerts, and a previous day’s countdown never auto-resumes.
Low battery
Banner suggests Low Power Mode; animations reduce; logging unaffected.
Opened on a second device
“Workout active on Maya’s iPhone — continue here? This pauses editing on the other device.” Continue on this device / Cancel. One device edits at a time; the previous device becomes read-only (“View only — workout continued on another device”). Takeover requested while the other device is offline is granted from the last synced server copy; the offline device keeps its unsynced sets, which merge into history (read-only) when it reconnects. Genuine conflicts use server version numbers, never device clocks.
